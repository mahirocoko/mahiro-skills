## Architecture Decisions

- Continue consuming upstream CocoIndex Code as the runtime engine; do not fork or patch its checkout for this correction.
- Treat Mahiro Skills as the portable policy owner and Mahiro Mods as the Letta runtime enforcement owner.
- Keep security fail-closed: stale settings/receipt, unsafe candidates, unsupported chunkers, or malformed limits block indexing.
- Preserve a truthful distinction between helper protection and upstream guarantees.
- Keep other projects with stale settings blocked until each is deliberately synchronized and strictly scanned rather than mutating tracked settings across repositories silently.

## AI Diary

This session was a useful reminder that “the tests pass” and “the security boundary is complete” are not the same statement. I initially felt close to done several times, but independent verification found concrete counterexamples: upstream rejected YAML null chunkers that our helper allowed, a stricter cap was not applied to strict-scan candidate scope, inline comments were dropped, and the final source rehash still fell back to the global 5 MiB ceiling. Each finding was narrow, reproducible, and worth fixing. The strongest part of the work was not the volume of checks; it was allowing the verifier to refute the claim and then tightening the exact evidence layer instead of defending the implementation. I also made one process mistake by letting an inventory command inspect CCC/Git filenames in the explicitly no-touch OneDee checkout. It did not read source bytes or mutate state, but the boundary was still crossed and should not have happened. I stopped using that checkout immediately and kept the rest of the work on explicit allowed roots. The final system is more honest now: upstream remains the indexing engine, while our Skill and Mod provide the controls we actually verified.

## Honest Feedback

Three friction points stood out. First, the implementation loop became repetitive because every verifier correction required reinstalling adapters, refreshing the overlay and receipt, rerunning the index, and then proving the live Mod path again. That repetition was justified after source changes, but earlier checkpoints could have been framed more explicitly as provisional to avoid premature “final” language. Second, the settings parser is deliberately line-oriented, so upstream YAML compatibility must be tested with exact installed behavior rather than inferred from “falsy” Python values or generic YAML semantics. Third, the distinction between upstream runtime and owned enforcement was easy to phrase imprecisely. Saying “we do not use upstream” would be wrong; we still execute upstream `cocoindex-code 0.2.41`, but we neither patch it nor rely on it alone for the security claims. Future work should state that architecture early: upstream engine, portable Skill gate, Letta Mod gate, and fresh receipt as the bridge.

## Lessons Learned

- Every effective file-size boundary must be passed through all content reads, including final TOCTOU rehashes—not only initial candidate filtering.
- Parser compatibility claims require probes against the exact installed upstream parser.
- A live active-Mod denial before database creation is materially stronger than source-only guard tests.
- Fresh verifier refutation is valuable when security claims span source, installed payload, and runtime state.
- Direct upstream invocation remains outside the owned cooperative guard unless it is routed through the Skill/Mod contract.
