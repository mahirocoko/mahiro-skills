# Direct CLI Monitor and Letta lane receipt contracts

## Session Summary

Aligned Mahiro Skills with two current Letta Code behaviors that intersect real
workflows: controller Monitors survive turn interruption until explicitly
stopped, and Letta subagent launch results now expose both Agent ID and
Conversation ID. Direct CLI remains callback-primary; only watcher/raw fallback
uses a controller Monitor. Control Room now records the complete Letta identity
pair when it creates Execution Run lane metadata. The pre-write pulse contained
31 prior retrospectives across 25 active days; this is today's first Skills
retrospective, and the pulse remains derived local context rather than canonical
telemetry.

## AI Diary

The most useful correction in this session was not technical; it was about
scope. I saw several new Letta Code capabilities and responded as though the job
were to maximize adoption. Mahiro wanted the opposite: identify only what the
existing ecosystem uses. Once I removed Grok OAuth, Cloud usage UI, native
Workflow, and unproven structured-output integration, the answer became much
cleaner. Direct CLI already has a watcher fallback that uses Monitor, and our
Execution Run procedure already records lane sessions. Those were the real
consumers.

I was careful not to let the Monitor update rewrite the callback architecture.
The new upstream behavior only means a controller Monitor remains alive when a
turn is interrupted. It does not make Monitor a durable callback ledger, does
not survive process restart, and does not replace exact Herdr receipts or final
report collection. The final wording now preserves those distinctions. I also
appreciate that the independent verifier did not turn source evidence into a
fake local integration test requirement. A portable skill repository should not
pretend it can simulate Letta's TUI interruption lifecycle. The weekly pulse was
flat before this entry; the meaningful progress was reducing speculative surface
area while strengthening two contracts we already rely on.

## Honest Feedback

1. My first ecosystem recommendation was too expansive and included Grok OAuth,
   even though Mahiro's Grok route is Cursor/Direct CLI and the new OAuth path
   does not solve a current problem. I should have mapped current consumers
   before listing upstream features.
2. The first implementation plan made Monitor persistence sound like a possible
   new subsystem. In reality it is a narrow lifecycle correction for watcher
   fallback. The callback path already has stronger receipt, ledger, and recovery
   ownership and should remain untouched.
3. Text-contract tests prove our packaged guidance cannot silently regress, but
   they do not prove Letta runtime behavior. I must continue labeling source-
   inspected version-specific evidence separately from executable tests owned by
   this repository.

## Lessons Learned

- Start release adaptation from current ecosystem consumers, not upstream
  feature novelty.
- A turn interruption is not Monitor cancellation; exact task identity remains
  live until explicit `TaskStop` or process exit.
- Never re-arm a watcher merely because the parent turn was interrupted.
- Callback-primary Direct CLI and controller Monitor fallback have different
  owners and must not be merged.
- A conversation ID is not sufficient Letta subagent identity when `default`
  may repeat across agents.
- Portable guidance should state runtime evidence boundaries instead of adding
  a test that cannot exercise the owning runtime.
