## Honest Feedback

First, the design consultation and initial implementation both framed usability around one selected skill, although the collection-level job was apparent from the manager context. A first prototype should have put representative rows and update states in front of Mahiro before investing in the detailed action screen. Second, two external writer lanes consumed substantial time in analysis/read states without touching files. Their accepted prompts were not delivery evidence; a first-edit checkpoint would have prompted a smaller assignment or Main implementation earlier. Third, writer-authored tests initially looked reassuring while an independent verifier found a real overwrite window across an awaited network call. Local preflight is not enough when an external response can arrive after files or lock metadata change. I corrected that by asserting the snapshot again immediately before invoking the installer and by adding the adversarial fixture. A smaller but telling issue was list-density at 72×18: a header that looked fine at desktop width hid the quit key, so I split controls into two lines and validated the actual terminal. The final tests establish mechanics and guards, not Mahiro's acceptance of the finished TUI.

## Lessons Learned

- For a collection manager, expose the collection decision first: fast local facts immediately, an explicit single read-only scan for expensive external facts, then selected-item detail and mutation. This differs from the existing batch-*write* confirmation lesson.
- Recheck mutable files, source, receipt, and link after awaited upstream I/O and immediately before an official installer call; preview checks do not substitute for mutation guards.
- An accepted external prompt is not a completed edit. A bounded first-write checkpoint and one checkout writer prevent an inert lane from blocking progress indefinitely.
