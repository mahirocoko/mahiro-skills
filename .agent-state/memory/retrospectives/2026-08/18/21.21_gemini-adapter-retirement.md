## Honest Feedback

Three friction points stand out. First, the initial repository scout failed after a WebSocket idle timeout, so it provided no value despite consuming time; for a bounded removal anchored in exact symbols, the main-agent search was enough and should have been the default. Second, my first retired-contract searches were too literal. They found `commands-gemini` and adapter lists but missed semantically stale guidance in `skills/learn/SKILL.md` and README. A migration audit should search both implementation identifiers and human-facing capability phrases before asking a verifier to certify alignment. Third, I nearly treated source completion and global cleanup as one operation. Separating them was safer: first implement and test a hash-bound migration, then audit the actual receipt, then perform the explicitly requested cleanup. The process was slower, but the boundary prevented unrelated user-installed skills from being removed. I should preserve that ordering for future installer retirements while reducing redundant full-suite runs until the textual contract audit is complete.

## Lessons Learned

- Adapter retirement is a context-contract migration: types, artifact inventory, installed transforms, TUI surfaces, docs, examples, tests, receipts, and live footprint all need one current owner.
- Never delete a retired adapter's installed files by filename pattern alone. Require exact root/scope, a validated receipt, one state per recorded item, and current hash equality.
- Standalone skill identity and installer-adapter identity can share a name; documentation must state that distinction explicitly to avoid accidentally deleting a still-valid skill payload.
- Exact grep is necessary but insufficient for capability removal. Include semantic prose patterns and use an independent verifier after corrections.
