## Honest Feedback

1. **Research fan-out หนักเกินขนาดของคำถามบางส่วน** — การแยก provider เป็นหลาย lane ช่วยลด blind spot แต่มี lane ที่ใช้ token และเวลามากกว่าที่จำเป็นสำหรับการตอบเชิง decision support รอบหน้าให้แต่ละ lane คืนตารางสั้นพร้อม source URL, unknown และ practical recommendation ก่อน ถ้าต้องขยายค่อยขอ deep dive เพิ่ม ไม่ควรให้ทุก lane crawl กว้างตั้งแต่ต้น
2. **Runtime freshness ยังหลุดจาก source policy ได้ง่าย** — Agy catalog รอบนี้รายงาน `1.1.7` แต่ canonical direct-cli note ยังมี historical `1.1.6` และ Gemini Pro เคย launch ไม่ผ่าน ถ้าผมตรวจแค่ catalog จะเขียนคำแนะนำที่ดูถูกต้องแต่ใช้งานจริงไม่ได้ การทำเอกสาร model ต้องมี availability check และ policy check คู่กันเสมอ
3. **Metric naming และ snapshot เป็น friction หลัก** — AA มีทั้ง composite, field ปัจจุบัน, effort variant และ leaderboard revision ขณะที่เอกสารเก่ามีชื่อ `Coding Agent Index` คนละช่วงเวลา ถ้าไม่ pin exact field กับวันที่ ผู้อ่านจะเปรียบเทียบเลขที่ไม่ใช่สิ่งเดียวกันได้ง่าย รอบหน้าควรเก็บ raw row หรือ evidence receipt ตั้งแต่เริ่ม research

## Lessons Learned

- Catalog presence ไม่เท่ากับ foreground launch proof
- Benchmark table ต้องบอก provider, exact model ID, effort, harness, field name และ access date
- Official vendor score ใช้บอก task-specific strength ได้ แต่ไม่ควรเรียกเป็น independent comparison
- Fallback, preview identity และ serving revision ต้องอยู่ในชื่อหรือ caveat ของ row ไม่ใช่ซ่อนไว้ท้ายเอกสาร
- Engineering role fit ต้องเริ่มจาก risk, feedback loop, tool state และ cost ไม่ใช่ rank เดียว
- Repo-local policy ปัจจุบันต้อง override ความรู้จาก catalog หรือ model page เมื่อสองแหล่งขัดกัน
- Research doc ที่ดีควรมี internal benchmark plan เพื่อเชื่อม public evidence กับ task จริงของทีม
