## Honest Feedback

Three frictions stand out. First, the original mock removal dependency unconditionally deleted the canonical folder, so the tests could never challenge the official CLI's retained-lock behavior. Future integration tests for external tools should assert their *observed postconditions*, not just exit status or a stub's ideal result. Second, my first interpretation of Mahiro's “ลอง computer-use” was a request to use the Computer Use capability rather than to uninstall that named skill. Inspecting the concrete named inventory row before choosing a workflow would have saved a detour. Third, recovery can be designed to reverse the pre-cleanup transaction, but once staged payload deletion begins, a crash may leave an incomplete payload that cannot safely be reconstructed. The manager must say so and retain a journal, rather than promise unconditional rollback. The full suite's one failing narrow-viewport assertion was a copy-wrapping issue, not the deletion algorithm, and I corrected it with a focused rerun instead of treating the earlier 371 passes as a clean suite. I should continue to separate these evidence scopes in release reporting.

## Lessons Learned

- A successful external remove command is not evidence that a shared global canonical root or lock entry was removed. Compare the exact postconditions and inspect source ownership before broadening flags.
- A global-skill manager needs two separate ownership checks: who installed the canonical skill, and which adapter links it may unlink after explicit confirmation. A verified external GitHub lock can establish the first without a manager receipt.
- Recovery must verify staged payload identity, content hash, and every destination before restoring lock/receipt metadata. Once destructive cleanup starts, manual repair can remain necessary.
