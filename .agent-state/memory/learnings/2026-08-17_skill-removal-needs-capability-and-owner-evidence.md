# Skill removal needs capability and owner evidence

Low invocation count alone is not enough to remove a skill. Evaluate at least:

1. **Unique capability** — does another current owner already perform the same job?
2. **Trigger shape** — is low usage expected because the skill is explicit, one-time, or safety-critical?
3. **Maintenance duplication** — are scripts, routes, docs, or command contracts owned twice?
4. **Default-install cost** — does every adapter receive a platform-specific or unrelated workflow?
5. **Regression shape** — can removal be guarded through exact package paths and slash identifiers without banning ordinary prose?

In this session, `philosophy` was safe to remove because it had no procedural capability and its durable principles already had stronger owners. `watch` was retained because it adds YouTube metadata, caption retrieval, and local learning-note capture beyond Gemini transport. Its contract was repaired by aligning the research URL with the current Gemini owner and adding a direct static regression test.

When removing a packaged skill, update the canonical skill tree, both command wrapper families, default manifest, README/discovery indexes, count assertions, and exact retired-path guards in one migration. Keep provider-runtime claims scoped: source and tests can prove route alignment, not authenticated external behavior.
